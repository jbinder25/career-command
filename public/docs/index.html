Developer guide

How this career app is built, how its pieces talk to each other, and where to change things. Read top to bottom once, then use the contents as a map.

Overview

A private job-search workspace for one person. It has three jobs:

TrackOpportunities, stages, next actions, interviews, contacts and documents at /career.
DiscoverA scheduled scan reads company job boards, filters by your rules and queues new postings.
TailorPicks approved resume bullets and drafts a cover letter from facts you supplied.

There is no build step and no framework: static HTML pages in public/, a login gate in middleware.js, three small serverless functions in api/, and a Supabase (Postgres) database. Only public/ is published.

Free mode is the default. With no AI key set in Vercel, discovery and surfacing run on Vercel cron and the AI steps (scoring, tailoring) are done by Claude sessions on your Claude plan through the Supabase connector. See Job agent pipeline.

Architecture

  • Browser to Supabase: the tracker uses supabase-js with the signed-in user's token. Row-level security decides what it can see.
  • Vercel Cron to /api/job-scan: sends Authorization: Bearer $CRON_SECRET. The function then calls the database through public.job_agent_rpc with JOB_AGENT_SECRET.
  • Scheduled Claude task to Supabase: the Supabase connector runs SQL as the project owner, so it calls private.job_agent_op directly. No secret is needed.

Data model

The complete schema is supabase/schema.sql (run once on a new project). supabase/migrations/ is history only.

job_leads.status moves through: filtered (dropped by hard rules), pending (waiting to be scored), scored, review (shown in the Leads tab), then accepted or rejected; error after a failed scoring attempt (retried up to 3 times). Accepting a lead creates a jobs row and links it through job_id.

Auth and security

  1. Magic link. /login asks for an email, checks it against ownerEmails in public/shared/config.js, and asks Supabase Auth to email a sign-in link (no passwords).
  2. Sign-up gate. A trigger on auth.users (private.only_owner_signup) rejects any sign-up whose email is not the one in private.job_agent_config. With no config row, everyone is blocked.
  3. Cookie. After sign-in the login page stores the access token in a jic_at cookie (Secure, SameSite=Lax).
  4. Gate. middleware.js runs on every request except /login, /favicon.ico, /shared/theme.js, /shared/config.js and /api/job-scan. It validates the token with Supabase (/auth/v1/user, cached for up to 5 minutes) and requires the email to be in ownerEmails. Pages redirect to /login; /api/* returns 401 JSON.
  5. Row-level security. All tables have RLS on. Restrictive policies call public.is_owner(), which compares the token's email to owner_email. Even a valid account that is not the owner reads nothing. Storage objects in the career-documents bucket have the same rule.
  6. Job agent secret. public.job_agent_rpc(p_secret, p_op, p_payload) is callable by the anonymous role, but raises unauthorized unless sha256(p_secret) matches the stored hash. The logic lives in private.job_agent_op, which only the database owner and service roles can run. /api/job-scan itself requires CRON_SECRET.

What is public and what is not. The Supabase URL and publishable key in config.js are meant to be public (RLS protects the data). Never commit CRON_SECRET, JOB_AGENT_SECRET, an AI API key, or a Supabase secret or service-role key. Keep the repository private: it holds your career history.

Job agent pipeline

Four stages. The first and last always run on Vercel; the third runs on Vercel (API mode) or in a Claude task (free mode).

  1. Discover. Read every board: the favorites in companies.json (tiered) and the open boards in open-boards.json (found by scripts/discover-boards.mjs from company-seeds.txt). Boards for favorites are guessed from the name and remembered in job_sources. New postings are saved to job_leads; postings no longer listed are marked closed.
  2. Filter (no AI cost). search.json rules: title must be a target role and level (or the optional stretch level at a higher pay bar), location must match the home metro or US-remote, the posting must be recent, and pay must clear the floor when stated. Failures are stored as filtered with the reason.
  3. Score. Pending leads (favorites first) are evaluated against rubric.md and scoring-instructions.md, with your 25 most recent accept/reject decisions as calibration. The result is category scores, a total, a recommendation, dealbreakers and the report text shown on the lead card. A favorite-tier bump is added after scoring (tier_bump).
  4. Surface. A scored lead goes to review only if its score meets the bar (default 80), it has no dealbreakers, its location is eligible, it is not "Do not recommend", and its pay clears the pay bars (unlisted or borderline pay needs 90+). The best go first, up to the daily cap (default 15 per local day), from leads first seen in the last 14 days.

Cron schedule

vercel.json defines three cron jobs calling /api/job-scan?slot=morning|midday|evening at 11:00, 17:00 and 23:00 UTC. They are separate jobs because Hobby allows each job to run only once a day. Times are UTC; change them in vercel.json. Each call runs discover, score and surface in order.

Run a step by hand

http
GET /api/job-scan?step=discover&key=<CRON_SECRET>
GET /api/job-scan?step=score&key=<CRON_SECRET>
GET /api/job-scan?step=surface&key=<CRON_SECRET>

The response is JSON stats (boards_ok, new_postings, scored, surfaced, ...). A fatal field means the run stopped. Each run is also logged in job_agent_runs.

The scheduled Claude task (free mode)

A scheduled Claude Code task on the repository, with the Supabase connector attached, follows docs/claude/score-leads.md: fetch pending leads with private.job_agent_op('pending'), read the brief with scripts/leads.mjs, write evaluations, save them with save_score, surface, and log the run. Daily is enough.

Tailoring

api/_lib/tailor.js builds all prompts from knowledge/profile.json and the documents it lists. The model never writes a resume freehand: it selects approved bullets from knowledge/resume/resume-library.md (tagged by topic; variants of one achievement share a tag), lightly rewords them, and code composes the resume and checks it against the style guide (about 450 words, at most 12 bullets). The cover letter is checked for length (250 to 330 words), clichés and signature.

  • In the app (API mode): the Tailor button calls POST /api/tailor. It needs ANTHROPIC_API_KEY.
  • Free mode: without the key the page shows a copy-and-paste instruction for a Claude Code session, which follows docs/claude/tailor-with-claude.md using the same prompts and saves the drafts as activities on the job.
  • Facts: only from the files in profile.json sources. The job description is treated as untrusted text.

Print the exact prompts any time:

sh
node -e "console.log(require('./api/_lib/tailor').SYSTEM)"

scripts/leads.mjs is an offline helper used by the scoring task. It makes no network calls and touches no database; the Claude session moves JSON between Supabase and the script.

Testing

sh
npm ci
node --test            # or: npm test

The tests cover the config shape (and that the Supabase URL appears only in config.js), the job filters and surfacing rules, the board readers, tailoring limits and style checks, the leads.mjs helper, and the theme script. Run them before every push.

Deploying

  1. Edit files, run node --test.
  2. Commit and push to the default branch. Vercel builds automatically (the build command only echoes; public/ is served as is).
  3. Wait for the deployment to be Ready, then open the production URL and check /login (200), /career (signed out, redirects to /login) and any page you changed.

Only public/ is published. A page placed anywhere else is not served. Link to clean URLs such as /career.

Database changes: add supabase/migrations/<yyyymmdd>_<name>.sql, apply it to the live project, and fold the same change into supabase/schema.sql so a fresh project matches.

Updating from upstream

This app began as an exported template. When a newer export is available, merge it on a branch. Keep your own public/shared/config.js, everything under knowledge/, and any edits to vercel.json. If supabase/schema.sql changed, apply only the new statements to your live database (never re-run the whole file on a project with data). Run the tests, push, and verify the deployed site.

Troubleshooting

SymptomLikely cause and fix
Magic link opens localhostSupabase, Authentication, URL Configuration: set Site URL to your site address.
"That email does not have access."The email is not in ownerEmails, or the private.job_agent_config row is missing or has a different email.
Every /api call is 401 "Sign in required"Session cookie rejected. Sign out (/login?logout=1) and in; check config.js points at the right project.
/api/job-scan is 401 or 503Wrong key (must equal CRON_SECRET), or JOB_AGENT_SECRET not set. Redeploy after changing env vars.
job_agent_rpc: unauthorizedThe Vercel JOB_AGENT_SECRET does not hash to secret_sha256 in the config row.
Cron not runningCheck Vercel, Settings, Cron Jobs, and the newest job_agent_runs rows. Hobby limits each job to once a day.
Leads stay pendingNormal in free mode until the scheduled Claude task runs. Check it is enabled and has the Supabase connector.
Supabase requests time outFree projects pause after about 7 days idle. Restore the project in the dashboard; the daily cron keeps it awake afterwards.
"Tailoring here needs an API key"Free mode. Use the pasted instruction in Claude Code (docs/claude/tailor-with-claude.md), or set ANTHROPIC_API_KEY.
